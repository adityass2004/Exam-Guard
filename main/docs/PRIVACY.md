# ExamGuard Privacy Policy & Biometric Data Handling

This document specifies the privacy architecture, cryptographic controls, retention limits, and student rights implemented in ExamGuard.

---

## 1. Biometric Data Collection Principles

1. **Purpose Limitation:**
   Facial images and embeddings are collected solely to establish a verified biometric identity reference for candidate verification before and during proctored examinations. Data is never used for secondary purposes, marketing, surveillance, or commercial facial profiling.
2. **Explicit Consent First:**
   No camera feed is analyzed or captured without explicit affirmative consent (`POST /api/v1/student/consent/biometric`). The canonical consent agreement text and its SHA-256 hash are recorded with timestamps in `consent_records`.
3. **Data Minimization:**
   - Previews are ephemeral: the real-time quality check loop (`POST /api/v1/student/enrollment/preview-check`) runs entirely in memory without writing files or database rows.
   - During examinations, only opened security incidents retain a single evidence snapshot. Continuous verification logs contain similarity scores and timestamps, **never raw image bytes**.

---

## 2. Storage & Cryptographic Protections

ExamGuard enforces cryptographic isolation at rest using two distinct 256-bit AES-GCM keys:

| Biometric Artifact | Storage Location | Encryption Method | Key Reference | Plaintext Access |
|---|---|---|---|---|
| **Enrollment Photos (5 poses)** | `storage/enrollment/<aa>/<uuid>.bin` | AES-256-GCM | `IMAGE_ENCRYPTION_KEY` | Restricted to authorized proctor review endpoints (audited) |
| **Incident Evidence Photos** | `storage/evidence/<aa>/<uuid>.bin` | AES-256-GCM | `IMAGE_ENCRYPTION_KEY` | Restricted to authorized proctor review endpoints (audited) |
| **Sample Embeddings (5 poses)** | MySQL `face_embeddings` (`kind=SAMPLE`) | AES-256-GCM | `EMBEDDING_ENCRYPTION_KEY` | Server-side only during centroid computation |
| **Centroid Reference Embedding** | MySQL `face_embeddings` (`kind=CENTROID`) | AES-256-GCM | `EMBEDDING_ENCRYPTION_KEY` | Server-side only during verification comparison |

### Critical Invariants:
- **No Image Bytes in MySQL:** Database tables (`face_enrollment_images`, `trigger_evidence`) store relative storage paths, SHA-256 checksums, and encryption metadata (12-byte random IV and 16-byte GCM authentication tag). Image binary data is never stored in relational tables.
- **No Biometric Endpoints for Students:** Students cannot download, export, or access raw embedding vectors or image files via API.
- **Memory Lifetime:** Decrypted biometric vectors exist in Node.js process memory strictly for the duration of centroid computation or similarity scoring and are not retained in global caches.

---

## 3. Log Redaction & Audit Integrity

- All system logs generated by `pino` automatically redact biometric keys, vectors, image buffers, base64 strings, and password parameters.
- Administrative access to enrollment images or evidence photos creates an immutable entry in `admin_audit_logs`.
- IP addresses recorded in audit logs are salted and hashed (`SHA-256(salt + ip)`) to protect network privacy while supporting forensic log correlation.

---

## 4. Student Rights & Data Deletion Workflow

- **Right to Request Deletion:**
  Students may submit a formal biometric deletion request at any time via `POST /api/v1/student/biometric-deletion-requests`.
- **Administrative Processing:**
  Deletion requests transition into `data_deletion_requests` (`status = PENDING`) for administrator fulfillment.
- **Fulfillment Effects (Phase 04 Implementation):**
  Upon administrative fulfillment via `POST /api/v1/admin/data-deletion-requests/:id/fulfill`:
  1. All 5-angle encrypted enrollment photograph files (`storage/enrollment/...`) are securely unlinked from disk storage.
  2. All database records in `face_embeddings` (both sample and centroid vectors) and `face_enrollment_images` for the student are permanently hard-deleted.
  3. All historical face profiles are marked `REVOKED` and `student_profiles.enrollment_status_cache` is set to `REVOKED`.
  4. The action is audited in `admin_audit_logs` (`action = BIOMETRIC_DATA_DELETED`) with **counts only** (`deletedImagesCount`, `deletedEmbeddingsCount`, `profilesRevokedCount`) — strictly zero biometric content is written to the audit log.
  5. *Institutional Policy Distinction:* Trigger incident evidence snapshots belong to examination disciplinary records governed by institutional exam retention schedules (P09); candidate enrollment deletion does not unilaterally destroy disciplinary incident evidence, representing an intentional institutional governance boundary.
